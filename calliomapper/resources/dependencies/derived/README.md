# Candidate OEO/PROV dependency compatibility derivations

These explicitly identified local derivatives are the dependency combination used by the current Stage 1 draft and evaluation. They are not official OEO or W3C releases. The originals remain unchanged in the parent `dependencies/` directory. The scripts verify their SHA-256 hashes before generating derived files. Both derived ontology IRIs are distinct from the official IRIs, and neither derivative imports the original source back into the same reasoning context. The files retain their original candidate notices and version identities; choosing this local validation contract does not represent publication or upstream endorsement.

## Why two candidates are necessary

The original dated PROV source declares `prov:wasRevisionOf` and `prov:specializationOf` as both annotation and object properties, and uses both predicates on its ontology header. The derived PROV file removes those two annotation declarations, preserves both header statements in `dependencies/derived/relocated-source-metadata.ttl`, and assigns an explicit derived ontology identity. All original vocabulary RDF triples outside those documented changes remain. Revision, specialization, derivation, qualified relationships, property chains, domains/ranges and disjointness are retained.

The unchanged OEO release independently declares **`prov:wasDerivedFrom` as an annotation property** for import provenance. It has 2,087 predicate uses and six triples describing that annotation property. This conflicts with the PROV object property when the ontologies are combined. Fixing only PROV is insufficient.

The derived OEO artifact renames that annotation predicate and its declaration/annotations to **`urn:ontocal:dependency:metadata:wasDerivedFrom`**. It does not rename or weaken the PROV object property. No OEO logical class/object/datatype axiom is removed. The source OEO file remains the original publisher-merged version; the candidate contains its full logical vocabulary, not a small extracted set of selected classes.

## Reproduce

From the repository root, use Python with RDFLib installed, Java/Javac, and ROBOT 1.9.7. The recorded environment used RDFLib 7.6.0 and Java 11.0.26. These commands perform no network access:

```sh
python dependencies/derive_prov.py
python dependencies/derive_oeo.py
python dependencies/verification/verify_candidate.py --timeout 180 --robot-jar /path/to/robot.jar
```

The ROBOT jar argument defaults to `robot.jar` alongside the resolved `robot` executable. All paths in the scripts resolve relative to their own directory. The current Python interpreter runs the derivations; use the same locked RDFLib environment when comparing generated bytes. The OEO candidate uses a deterministic direct RDF/XML transformation to retain source structure. PROV uses deterministic canonical RDF output. Auxiliary RDF fragments are audit views; blank-node identifiers in separate RDF documents are local and are not a portable patch format. The hash-checked scripts specify the actual reproducible transformations.

`verify_candidate.py` writes detailed command outcomes and times to `build/dependency-compatibility/candidate-results.json` and a summary to `build/dependency-compatibility/candidate-report.md`. Every subprocess has a timeout. Missing prerequisites or unfinished required checks are reported as unexecuted and cause a nonzero exit. Original profile rejections are tested as expected diagnostic failures and remain explicitly labelled with their observed nonzero exit codes. Add `--exhaustive-imports` to attempt supplementary satisfiability checks of every imported named class; its timeout remains visible without replacing the separate required local OntoCal class checks. Any actual failure, including an unsatisfiable imported class, produces a nonzero exit.

## What preservation means here

RDF-level checks show that only the listed declaration, metadata and header triples change. Independently, OWLAPI parses **4,004 unannotated logical OEO axioms** in both the original and candidate; the sets are equal. This demonstrates preservation of those logical axioms, not identity of annotation assertions or file bytes.

PROV requires a more qualified statement. OWLAPI parses 181 unannotated logical axioms in each file, but the sets differ in four places. The two original source-document object-property assertions are relocated to the sidecar. In the candidate, the existing RDF range statements for revision and specialization parse as object-property ranges to `prov:Entity`; the original punned source parsed those as annotation ranges. This explicit parser-level change is retained and tested rather than hidden behind an equivalence claim.

Consequently, these artifacts are **not claimed equivalent to the complete original RDF graphs**. They preserve the intended PROV object-property vocabulary and the OEO logical class/property axioms while changing how ontology-source metadata is represented. Their use is an explicit condition of the current OntoCal validation contract and must remain documented in any later release.

## Verification scope

The suite checks candidate OWL 2 DL profiles, combined reasoning, and small provenance examples. Positive cases check revision-to-derivation, specialization-to-alternate/Entity typing, responsibility association, generation and qualified revision chains. A negative case attributes a PROV Activity as if it were an Entity and must be inconsistent. Two absence-of-entailment checks guard against accidental Entity/Activity and Activity/Agent classification; their scope is only the tested fixture.

These are bounded tests, not a proof of every PROV requirement or interchange property. OWL consistency does not establish conformance with all temporal rules in PROV-CONSTRAINTS. Neither these checks nor logical-axiom comparison demonstrates OntoCal competency-question coverage, source-value fidelity or scientific modelling adequacy.

## Header changes and observed limitations

Each candidate receives its own ontology IRI and version IRI, an explicit derived-candidate notice, and a source reference. The original header annotations are copied to the candidate header except the version declarations and, for PROV, the original label. PROV's second empty ontology declaration is removed. `removed-header-triples.ttl` and `added-header-triples.ttl` isolate its header changes; `oeo-header-removed.ttl` and `oeo-header-added.ttl` do the same for OEO. The manifests use paths relative to `dependencies/`. Original attribution and licence records remain in that directory.

The historical evidence is in `docs/evidence/2026-10-16/dependencies/`. The combined candidates passed the OWL 2 DL profile; HermiT confirmed consistency with the positive fixture and the expected inconsistent negative fixture. Full classification and exhaustive class satisfiability each exceeded a 180-second bound. The current runner checks consistency directly and offers exhaustive imported-class satisfiability as a separate supplementary operation. It records any timeout as unfinished and exits nonzero when a required check is unfinished. It does not treat selected consequence tests as exhaustive ontology validation. Current evidence is in `docs/evidence/2026-10-22/dependencies/`.

On 22 October the complete supplementary direct satisfiability check finished in 274.406 seconds under a 300-second bound: all 1,620 named classes, excluding `owl:Nothing`, in the combined dependency signature were satisfiable. All required integrity, profile, axiom comparison, consistency and selected PROV consequence checks also passed. This resolves the earlier imported-class satisfiability timeout for these exact derivative files; it does not establish PROV-CONSTRAINTS conformance or compatibility with an arbitrary external import closure. ROBOT 1.9.7 supplied OWLAPI 4.5.29 and HermiT 1.4.5.456, running on Java 11.0.26.
